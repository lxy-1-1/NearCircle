# 面试讲解与动手练习

## 先说清楚项目的范围

> 近友是 Java 原生 Android 熟人社交项目，包含好友关系、单聊和朋友圈。我重点研究移动网络不稳定时的消息可靠性：Room 本地队列、WorkManager 重试、服务端幂等、HTTP 游标补齐及账号切换隔离。服务端是 Spring Boot + H2 的单实例实现，验证了功能和故障场景，没有做商用并发规模的承诺。

介绍自己的工作时请按实际贡献调整。AI 辅助生成、你亲自修改和独立完成的部分分别是什么，要能够诚实说明和现场演示。

## 现场可演示的五件事

1. 两个账号注册、搜索、发申请、接受；未经同意不能聊天。
2. 在聊天页断网，点击发送看到待发送；关闭并重新打开 App，联网后对方仅收到一条。
3. 发完消息切换账号，检查其他账号的本地会话与待发消息不混入。
4. 好友发朋友圈，非好友用相同 API/媒体 ID 请求被拒绝。
5. 运行提交顺序、迟到 401、图片取消和加载中刷新回归，解释最初为什么失败。

## 应当能回答的问题

- 为什么用 WorkManager？它与普通线程、前台服务各有什么边界？被强制停止后能否立即发消息？
- client_id 为什么必须在第一次发请求之前持久化？仅由客户端去重够不够？
- 为什么不能用 MAX(serverId) 作为同步游标？
- 自增 ID 是否等于提交顺序？并发双向发送怎样漏消息？怎样设计更可扩展的会话序列？
- HTTP 401、403、409 与 503 的处理有什么不同？重试是否会创造重复副作用？
- Activity 重建后哪些状态保留在 ViewModel，哪些在 Room，哪些来自服务端？
- WebSocket 通知丢了怎么办？它是否承载了可靠投递协议？
- 好友图片为什么不能直接提供不鉴权的 URL？怎么防止上传压缩炸弹？
- 为什么 PNG 重编码可能让 JPEG 变大？元数据去除与像素尺寸是两类限制。
- 如果需要 10 万日活，你将如何测量瓶颈、拆会话锁、替换数据库和补充监控？不要直接说“加 Redis 就行”。

## 建议亲自完成的改进

选择其中一个独立完成、补测试并记录前后证据，比继续堆功能更适合面试：

- 为聊天历史做 Paging，测量 1 万条本地记录的首屏时间与内存。
- 为单个会话提供发送顺序编号，降低当前双用户锁对不同聊天的影响。
- 增加统一的待发状态管理：认证过期、对方关系变化与网络超时分别展示。
- 把首页拆成职责明确的组件，用测试保证分页/刷新行为不变。
- 增加媒体清理策略，验证删除动态后未引用资源的回收。

记录设备型号、数据量、测量方法、失败结果与限制；不要把模拟器结果写成真机或生产数据，也不要编造用户数、吞吐量和获奖情况。
